# 第 2 期：任务源打通（tasks.json → 派单 → 执行 → 互审）

日期：2026-11-09。第 1 期已于 2026-11-09 19:24 经用户拍板关期
（注记：跨机主链已证明；「会话内 push」被 B 沙箱两条硬限制挡住、
分支由宿主补推成立——本期正面解决 push）。

## 本期目标

让一个**真任务**能走完全环，中间只经用户两次拍板（批准任务、批准合并，
合并在本期试点里以「评审 PASS 即止」代替，不真合 main）：

```
用户在 A 机项目里用 kit 把 task 置 approved
  → 桥自动 emit 一次（幂等，同项目串行）
  → 执行者（异机 DSH/Codex）按任务包干活，只 commit 不 push
  → 宿主侧补 push（本期落地）
  → 评审者（异机、异 Agent）评审，FIX 往返 ≤3 轮
  → PASS 收尾；僵局或超限出卡给用户
```

## 三个关键设计（本期写死，别再各行其是）

1. **任务包走 git，派单只发短句**。任务的长内容（背景/范围/验收）写成仓库里的
   任务包文件（格式见同目录 `TASK_PACKAGE.md`），hub 事件的 prompt 只发固定
   短句模板。这样绕开第 1 期补单实测的两个坑：argv 传长文本会丢双引号、
   `dsh.cmd` 会截断换行。
2. **push 双轨**。轨道一（落地）：执行会话只 commit；run 结束后由**宿主侧**
   补推（B 侧固定脚本 + A 侧规则触发，见两份 PROMPT）。轨道二（探针）：
   双机各测一次「会话内 push 到 GitHub https 远端」是否可行——
   若可行，真项目（GitHub 托管）可不用宿主补推；若不可行，宿主补推就是
   全项目的标准路径。探针只测不改判据，结果如实记录。
3. **评审落文件、结论走事件**。评审者把评审写成文件（报告仓或任务分支的
   `REVIEW.md`，以能落盘为准），hub 事件 summary 只带结论词：
   `PASS` / `FIX`（附条目数）/ `BLOCKED`。代码改动永远只由执行者做，
   评审者不改被审代码（拍板策略 v1 不变）。

## 继承的既有约定（不重议）

- 拍板策略 v1：单任务上限 6 轮、单轮 30 分钟、评审上限 3 轮、失败自动重试
  1 次；合 main/上线、改目标/范围/策略、动钱与凭据、装软件改系统配置、
  对外发送、僵局、跨项目动手——出卡等用户。
- 分支命名 `task/<任务号>-<短名>`；DSH 调用一律绝对路径、不改 PATH、
  不升级；凭据只经各机既有本地通道，不进 rules/报告/仓库。
- kit 约定：GOAL 改动须用户批准；tasks 只经 `kit.py task` 改；
  CURRENT ≤50 行。

## 本期关期标准

1. 桥：一个 approved 任务只 emit 一次（重复轮询不重发，有台账可查）；
   同项目已有在飞任务时，第二个 approved 任务被挡住并留痕。
2. 试点任务 1（A 派 → B 执行 → A 侧评审）走完全环：任务包文件入仓、
   B 只 commit、宿主补推成功（远端 ref 可查）、评审结论落文件；
   若有 FIX 往返，轮次 ≤3 且每轮有记录。
3. 试点任务 2（A 执行 → B 评审）同样走完，方向相反，证明互审双向可行。
4. GitHub https 会话内 push 探针双机都有明确结论（成功/失败原文）。
5. 第 1 期收尾完成：两条临时冒烟规则已删（备份在先）、DECISIONS 已记
   第 1 期关期。
