## 3. 建议部署结构

- A：唯一调度中心，同时运行执行端；管理队列、统一入口和控制项目的治理账本。
- B：执行端，主动连接 A 领取任务和回传结果。
- 两机经加密私网互通。优先复用已安装且可用的连接方案；没有时由 DSH 提出一个具体方案及需要新增的组件。
- 每个业务项目固定主要执行机器。首版不同项目可并行，同一项目最多一个写入任务；手工接管前暂停该项目后台任务。
- 每台先运行一个开发任务，全局先允许两个；这是待实测的起始配置，不是模型服务已确认的并发额度。
- 模型凭据各自在本机管理，不把 A 的登录文件复制给 B，不把密钥放进规则、Git、交接文件或普通日志。
- A 上控制工程账本只由 A 更新。B 提交结果材料，不双向同步或直接改 A 的 `.agent/`。业务项目的 `.agent/` 留在该项目所属机器上。
- A 不可达时不领取新任务；B 已启动的任务按原范围执行并本地保留结果。恢复连接后补交，不自动把原工作转到另一台重做。

建议文件位置：A 的本目录继续作为控制与交接目录；fork 的源码放 `app/` 子目录，保留根目录已有治理文件。B 的运行目录由 T3 确认。不要因根目录已有文件而覆盖它们，也不要为方便克隆而删除治理文件。

## 5. 部署前置任务的详细内容

### T2：A 的环境、通道和项目盘点

执行内容：

1. 读取最新治理状态和本任务书，核对当前阶段；保留根目录现有文件。
2. 记录 Windows 版本、Node/Git/Python/各 Agent 版本与绝对入口。确认 DSH 的桌面入口和自动化入口是否为同一版本。
3. 检查后台进程能否取得与交互终端相同的必要配置。不能依赖终端里临时设置的变量或弹出的登录窗口。
4. 记录各模型通道名称、配置来源、实际模型 ID、账户/额度池的非敏感别名。只记录“本机凭据已配置/缺失”，不导出凭据。

6. 列出候选业务项目的实际目录、Git 状态、开发命令、数据/桌面软件依赖、所属机器、现有 `.agent` 状态。未选择项目时只建专用演练项目。
7. 检查休眠、自动更新重启、现有后台服务、通知方式和可用磁盘；只记录，不在盘点阶段顺便修改全局设置。

交付：`evidence/preflight/A.md`。每项标为已实测、仅文件确认或未验证，并给出时间和原始日志位置。

- 与 A 相比的版本差异、项目文件是否完整、依赖能否本地运行。

### T4：跨网络连接、机器身份与连接恢复

执行内容：

1. 盘点现有加密私网或 VPN，选择一个实际可用方案，写清两端地址别名、启动方式及恢复方式。
2. 验证 A/B 位于不同外部网络时仍可互通；同一局域网的成功不能替代此项。
3. A 的任务服务只允许预期的私网访问。服务若绑定所有地址，必须有可核对的访问限制，不能只凭“平时没有公网地址”判断安全。
4. 规划 B 的独立执行端身份，区分通知/管理入口与执行端身份；实际任务接口的错误凭据测试在 T10、T11 服务启动后完成。
5. 验证连接断开、重连、服务重启后的行为；不复制正在使用的数据库到 B，不做双中心自动切换。

## 6. 程序适配任务的详细内容

### T6：Windows 原生执行与生命周期

- 支持 Windows 绝对路径、空格、中文目录和实际 CLI 入口；正确处理 `.exe`、`.cmd`、`.ps1`，不拼接可被二次解释的命令。
- 替换对 `/bin/sh`、`ps`、Unix 进程组和 systemd/launchd 的直接依赖；保留原平台路径，改动尽量集中在平台边界。
- 正确保存启动状态、输出、退出码和结果；中心/执行端重启后可识别原任务，不重复启动。
- 停止/超时能结束所管理的子进程；后台启动不依赖可见终端和交互确认。
- 加入 Windows 原生回归检查，并保留上游要求的适用检查。不要只证明 TypeScript 编译通过。

交付：实际源码和检查改动、`evidence/windows-runtime.md`。
完成条件：Windows 上真实启动、停止、超时和重启恢复通过；没有遗留的业务子进程。

### T7：Codex、Claude Code/Go、DSH 的接口与会话

初始启用路径：Codex/OpenAI、Claude Code/DeepSeek V4.1 Flash。DSH 完成自身实测后再启用，不作为未经验证的替代路径。

- 各通道明确 executable、配置来源、provider/model、权限和会话 ID；每轮记录实际使用的通道，不只记录请求值。
- 不能只依赖 Claude 原生账户登录检查判断 Go 是否可用；核对当前 Go 凭据模式并做真实调用。
- 验证读取文件、受控编辑、运行检查、问题等待后恢复、取消、失败结果识别；权限不足应明确停止。
- 核对 DSH 已安装版本的 ACP 能力。研究时 Autoloop 使用 `session/load`，DSH 当前实现使用 `session/resume`；依据实际能力正确接通，不用“失败就新建会话”掩盖兼容问题。
- 显式验证 DSH 的模型和 reasoning 配置确实传入。研究时通用 ACP bridge 未把 `turn.model/effort` 应用到会话配置。
- 核对 DSH 到 Go 的实际模型路径是否传递稳定会话标识；当前官方文档列有部分路径未覆盖的问题。失败需修复明确接口或暂停该路径，不能伪造客户端身份。
- 分开记录套餐额度、可观测 token 和实际额外扣款。接口没有提供的数据标为未知，不填零冒充精确统计。
- 不把某种 Agent 的沙箱能力当成所有工具共有的能力；不为消除确认而全局切换到无限权限。

交付：实际接口改动、`evidence/adapters.md`；其中单列每种工具的安装版、调用版、模型 ID、接续/取消结果和未验证项。
完成条件：两条初始路径实测通过；DSH 全部专项条件通过才可启用，失败不影响已验证路径的事实记录。

### T8：Project Anchor 任务桥接与真实验收

- 通过已安装 Skill 的 runtime 定位治理程序，不硬编码 A 的路径给 B，不直接改受保护状态。
- 只领取已批准、依赖及当前材料证据有效、交付声明齐全的任务；草案、旧失效证据、变更后待重批任务不能启动。
- 每个项目固定主机和实际目录，读取当前任务 ID/范围，不按最近修改时间猜任务。
- 完成判断分清本轮进程结束、业务任务完成、独立验收通过。等待回答的进程结束不等于业务完成。
- 检查证据绑定实际交付物和当前代码版本；后续改动导致旧证据失效时重新验证。
- Review 查 Bug 后再检查能否简化；自查记录不得标成 Codex 独立验收或用户确认。
- 控制项目账本在 A；B 上业务项目的账本由 B 的治理程序维护，中心接收结果摘要，不同时远程写同一账本。

交付：桥接源码、演练项目及检查、`evidence/anchor-bridge.md`。
完成条件：未批准、依赖未满足和旧证据任务被拒绝；已批准任务能执行、验收、保存断点并接续。

### T9：路由、并发、额度和停止规则

- 先按已登记项目选择机器，再按明确批准的任务配置选择 Agent/model；不让模型临时猜测目录、权限或账户。
- 同一项目的所有写入规则统一限流；不能因规则名不同而绕过项目写入限制。两份路径对应同一项目时仍使用同一项目身份。
- 初始每机一个开发任务、全局两个；同订阅身份的用量一起核对，不认为两台电脑自动增加模型额度。
- 测试/格式检查/任务查询用普通程序；没有可运行任务时不反复唤醒模型。
- 设置明确的单轮时限、修复轮数和任务上限；DSH 在设计中填写具体值及来源。缺少准确扣费数据时，以可执行的轮数/时限为硬限制，费用显示未知。
- 连接故障可按已配置的有限策略重试；需求不清、权限不足、会话损坏、代码持续失败分别记录，不无限循环，不自动换模型/换会话重做。
- 关键审查发生在同一份代码材料上。DSH 与 Claude Code 都调用同一 DeepSeek 时，不能算两份独立模型验收。
- 手工接管能暂停项目；额度不足停止派发该账户的新任务，其他独立账户的任务按自身规则继续。

交付：调度改动、可分享的无密钥配置模板、`evidence/scheduling.md`。
完成条件：项目互斥、跨项目并行、停止/限额和空闲行为均有实际证据。

## 7. A/B 部署任务

### T10：A 部署中心、执行端和管理入口

1. 使用固定版本部署包，先导出旧配置和数据的可恢复备份；新安装则记录没有旧状态。
2. 在选定账户下注册 Windows 后台启动，确认日常运行与开机/登录后的行为符合该启动机制的实际限制。
3. 启动唯一中心和 A 执行端，绑定 T4 确定的访问范围；重复启动应明确拒绝或复用原实例，不能多开中心。
4. 接通一个可实际查看的管理入口，至少支持看项目/机器/任务状态、回答问题、暂停项目、停止任务及查证据。
5. 优先沿用现有 MCP/卡片入口；若需要额外页面，只做上述必要操作。未接好的入口不能在文档里标为可用。
6. 核对后台凭据可用、故障能被看见，日志与可分享报告已脱敏。
7. 服务启动后验证无凭据、错误凭据和错种类身份不能领取任务或修改状态，核对实际监听范围。

交付：`evidence/deployment/A.md`、A 的启动/停止/恢复说明和部署包清单。
完成条件：A 真机运行，可管理演练任务，后台重启后状态一致。

### T11：B 部署执行端

1. 接收 A 的同一部署包并核对内容哈希；使用 B 本机路径和凭据，不能整份复制 A 的私有配置。
2. 注册 B 的唯一执行端身份并连接 A；B 不启动第二个中心，不接管 A 的数据库。
3. 登记 B 的本机 Agent 入口与已验证模型通道；模型可用性由 B 本机实测确认。
4. 登记 B 所属项目目录，运行一个专用演练任务；检查结果从 B 正确回到 A。
5. 验证 B 后台重启和实际选用启动机制；完成前核对无重复执行端和残留进程。

交付：B 原始报告，汇总到 A 的 `evidence/deployment/B.md`；与 A 相同的部署包标识及 B 的差异配置清单。
完成条件：B 从不同网络领取并完成任务，A 可看到机器、模型、结果和证据；报告能定位到 B 原始执行日志。

### T12：DSH 双机演练、恢复与回退

- 在专用演练项目运行下节场景，不直接把真实业务项目当故障演练材料。
- 每个场景记录开始/结束时间、机器、任务和会话 ID、输入/输出材料哈希、命令、退出码及日志位置；涉及模型时记录实际模型。
- 验证停止派发、停止运行任务、导出数据、恢复配置和回退程序的步骤；备份可读取不等于可恢复，至少实际恢复一次演练状态。
- 恢复后重试结果提交不会重复记完成或重复派任务；以固定任务编号和执行编号核对。
- 汇总实际修改的全局配置、后台组件、监听范围和卸载方式；不能把只存在本机的秘密打包进证据。

交付：`evidence/rehearsal.md`、`evidence/rollback.md`、`evidence/manifest.json` 及对应原始日志。
完成条件：DSH 对每个场景逐项写出实测结果和未通过原因，准备给 Codex 的可复现入口；不要自行生成“独立验收通过”结论。

## 8. Codex 独立验收与真实项目启用

### T13：Codex 验收清单

DSH 交付后，Codex 先读取实际源码、工作区改动、部署版本和日志，再实际复跑；修改任何受测材料后，重跑受影响项。

| 编号 | 验收场景 | 必须观察到的结果 |
| --- | --- | --- |
| V01 | A/B 位于不同网络 | B 能连接指定 A；错误身份不能领取或改状态 |
| V02 | 两机程序版本 | 基础版本、修改内容和部署包哈希能对上 |
| V03 | 两个不同项目同时执行 | A/B 分别完成各自任务，结果归属和证据正确 |
| V04 | 同一项目两个写入任务 | 后一个等待；不同规则、路径别名不绕过限制 |
| V05 | 草案、依赖失败、旧失效证据 | 均不进入执行；已批准且依赖有效任务能进入 |
| V06 | 等待用户选择后接续 | 业务状态显示等待；结束等待进程；回答后续同一任务，不重做已完成部分 |
| V07 | Codex 会话与实际模型 | 实际通道可核对；恢复、失败、取消结果真实 |
| V08 | Claude Code/DeepSeek 会话 | B 和 A 各自实测；实际模型、编辑、检查、接续均可核对 |
| V09 | DSH 专项 | 安装版恢复协议、实际模型、Go 会话标识和取消通过后才启用；未通过明确保持禁用 |
| V10 | 业务检查失败 | 不显示任务完成、不生成通过证据；修复受限于批准范围和轮数 |
| V11 | 停止与超时 | 不再继续写入，托管子进程结束，结果不能误记成功 |
| V12 | 执行中重启 A 中心 | 不重复启动原任务；恢复后可追踪原结果 |
| V13 | 执行中重启 B 执行端 | 原进程/已完成结果能正确识别，不再次执行同一业务 |
| V14 | 网络断开和恢复 | 无重复派发；B 本地结果保留，恢复后只登记一次 |
| V15 | 手工接管项目 | 暂停后不启动新写入任务；运行中任务按明确停止/完成方式交接 |
| V16 | 限额、修复轮数和空闲 | 达上限能停，空闲不唤醒模型，不隐式换模型继续 |
| V17 | 启动机制与重启 | A/B 按各自注册方式实际重启验证；依赖登录的方案如实注明 |
| V18 | 管理入口 | 用户实际能查看、回答、暂停、停止和定位证据 |
| V19 | 回退恢复 | 恢复演练状态可运行，保留原任务与证据，不清空未知业务文件 |
| V20 | 版本变化后的证据 | 修改后旧结果不会继续作为当前验收通过 |

验收结果分为通过、失败、未验证。未验证不得计为通过；报告通过/失败/未验证数量，并只展开关键问题。
若 Codex 无法实际操作 B，B 项标为“仅审核 DSH 证据，未独立实机复验”，不得宣称完整双机验收通过。
DSH 禁用时，可以明确交付“Codex+Claude Code 双机已验收、DSH未验收”的受限范围，不能称为三工具全部完成。
独立验收报告由 Codex 生成 `evidence/acceptance-codex.md`；Project Anchor 中的 claimed/self 记录不能冒充此项。

### T14：两个真实项目小范围启用

- 用户明确指定两个项目及其所属机器、任务范围和验收条件后再启用，不能从历史聊天猜项目。
- 接入前检查真实 Git 改动与 `.agent` 状态，保留现有工程，不自动迁移旧账本或更改目标。
- 每个项目先推进一个已批准小任务，依次验证执行、检查、保存证据、接续下一项的真实流程。
- 用户手工工作与后台工作之间明确接管；不自行开启额外并发、自动提交、推送、合并或发布。

交付：`evidence/pilot.md`，记录实际项目、任务、版本及通过/失败/未验证数量。
完成条件：真实项目结果与批准范围一致，由 Codex 复验；未选定真实项目不阻塞专用项目的部署演练。
