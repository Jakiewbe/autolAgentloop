# T9 调度与并发：按机器、按任务、按上限

任务书要求：先按项目选机器，再按任务选 Agent 与 model；同一项目写入统一限流；初始每机 1 个开发任务、全局 2 个；两台电脑不增加模型额度；没任务不反复唤醒模型；单轮时限、修复轮数、总量上限给具体值；缺扣费数据就以轮数/时限为硬限、费用记未知；不自动换模型、不自动重开会话；关键审查用同一份代码材料。

每条都落到这台机器上真实存在的旋钮（文件名:行号），并标出「已设置 / 待设置 / 不可设置」。

## 1. 先按项目选机器，再按任务选 Agent

- 机器由配置决定，不由事件决定：`config.json` 里的 `worker.name` 就是这台机器的身份（A 是 `desktop-lm7rki1`）。事件里的任何字段都改不了它。
- 一个项目只在一台机器上跑：规则里写死 `cwd`（`protocol/rules.ts:65` 校验：`~/`、`/`、盘符、UNC），`to` 写死 agent。事件改不了 `cwd`、`to`、权限（`kernel/decide.ts` 的规则匹配只按来源与类型）。
- 任务级 Agent/model：agent 条目支持 `model`、`effort`、`timeout`（`kernel/rules.ts:5`），worker 把它们透传给适配器（`worker/worker.ts:169-170`）。适配器支持才有意义：`command` 适配器会把 `{model}`/`{effort}` 替换进命令行（`plugins/command/agent.ts:9-10`）；codex CLI 自己决定模型，`{model}` 不填就是空串。DSH 的 ACP 侧没有 prompt 级 model 入口（T7 报告 §5），所以 DSH 只走 `session/set_config_option`。
- 结论：模型选择写在 agent 条目里，不写在事件里；跨机器分发靠规则各自绑定，不做「一个任务两台机器都跑」。

## 2. 并发上限（有具体值）

| 层 | 旋钮 | 值 | 状态 |
|---|---|---|---|
| 单机同时跑几个 | `config.json` 的 `worker.capacity`（`host/up.ts:82-83`；代码默认 2，`worker/worker.ts:132`） | **1** | A 已设为 1（18:47 改、备份 `config.json.bak-20261104-190000`）；B 接入时同样设 1 |
| 全局 | A 1 + B 1 | **2** | 只有 A 在线，实际 1 |
| 同一规则组 | `rule.parallel`（`protocol/rules.ts:82` 正整数；不写=1，`kernel/decide.ts:238`） | 不写 | 都不写，保持每组 1 |
| 同一事项分道 | 有 `parallel` 时 `lane = subject`（`kernel/decide.ts:137`） | 不用 | 同一事项不并行 |

为什么是 1：一台机器上并发跑两个真实 Agent 会同时吃 CPU 与额度，且两个都会往同一个仓库写；1 个就是为了「同一项目写入统一限流」。要提并发，先有 B 机分担（另一台机器的 1 个），不是在本机加。

## 3. 单轮时限（有具体值）

- 旋钮：agent 的 `timeout`，单位**分钟**（`protocol/rules.ts:163`；`worker/worker.ts:259/346`），默认 **180 分钟**（`worker/worker.ts:173` 常量 `TIMEOUT_MINUTES = 180`）。
- 建议值：开发任务 **30 分钟**，轻任务（查、答、巡检）**10 分钟**。超时按「停止」处理，记录 `why=timeout`，不留子进程。
- 参考实测：codex 单轮问答 21 秒（探针）、opencode 单轮 7 秒、试跑两轮各约 40 秒；180 分钟对开发任务太宽，等于不设限。
- 未设置：现有 `试一下` 规则没有写 `timeout`，还在吃默认 180。接入真实项目规则时必须写。

## 4. 修复轮数与重试（有具体值）

| 项 | 值 | 依据 |
|---|---|---|
| 同一轮内「同一会话续修」次数 | **2**（`REPAIRS = 2`） | `worker/worker.ts:37`、`:286` |
| 回执读不懂时 | 不再修，按第一行算结束，并推卡片说明原文位置 | `worker/worker.ts:234-246` |
| 一轮失败后重派 | 5 分钟起，每次翻倍，最多 60 分钟（`min(5·2^{n-1}, 60)` 分钟） | `kernel/decide.ts:262` |
| 第 3 次仍没结果 | 通知本人 | `kernel/decide.ts:282` |
| 会话接不上 | **不重开新会话**：这一轮记失败、写明「接不上原来的会话」，回到下面的重派上限 | `worker/worker.ts:264-274`（19:5x 改：删掉原来的 `triedFresh` 自动重开分支） |
| 一次派单最多派几次 | **5 次**，到第 5 次失败后停（`MAX_ATTEMPTS = 5`），状态记 `unknown` 并推一张「不再自动重派」的通知 | `kernel/decide.ts:31`、`:284-294` |
| 租约/离线 | 领取后 5 分钟没动静算存疑（`RUN_LEASE`）；worker 2 分钟内没心跳算新鲜度不足（`WORKER_FRESH`）；等 worker 超过 10 分钟告诉本人（`OFFLINE_AFTER`） | `kernel/due.ts:8-12` |

**总量上限**：一次派单最多 **5 次**派发（`MAX_ATTEMPTS=5`，`kernel/decide.ts:31`），退避 5→10→20→40→60 分钟；第 3 次失败先通知一次（`:296-301`），第 5 次失败即停：状态置 `unknown`、写「自动派了 5 次都没跑完，已停止自动重派」、推通知，不再排进 `queued`（`tests/kernel.test.ts` 新用例：连跑 10 轮只发生 5 次派发）。每轮内部还有单轮时限（`agent.timeout`）与最多 2 次修回执。

19:47 之前这里写的是「没有无限重试路径」，但代码里只有退避、没有总量上限（Codex 验收复现：连续失败 10 次仍在排队）——那句是错的，已按上面的实现改正。

## 5. 没任务时不唤醒模型

- 接单程序是长轮询：`/v1/work?wait=...`（`worker/worker.ts:417-422`，`WAIT=50` 秒），没有活就等；网络断了就 30 秒重试（`PAUSE = 30_000`）。
- 中台只在有到期的活时才派：定时由 `kernel/due.ts` 算，空转不产生模型调用。
- 实测：18:47 重启到现在，没有任何自发的模型调用（`status` 一直是 `今天 3 轮`，除我手动发的事件外没有增加）。

## 6. 费用：未知就记未知

- `status` 一直显示「Token 没上报 · 费用没上报」：codex CLI 的 `--json` 有 usage 但当前 `command` 适配器只读最后一条消息，不上报 usage；opencode 的 `--format json` 有 cost 但同样的原因没进账本。
- 所以硬限只能是**轮数 + 时限 + 并发**，费用一律记「未知」，不填 0。T13 验收报告里同样要写「费用未知」。

## 7. 不自动换模型、不自动重开会话

- 模型写在 agent 条目里，运行时不会被改写；失败不会切到别的 agent（`to` 由规则固定）。
- 会话接不上就停（`worker/worker.ts:264-274`）：不自动新建会话、不重跑提示词，只回到受上限约束的重派路径。这样「不自动换会话重做」在代码里成立，而不只是写在文档里。
